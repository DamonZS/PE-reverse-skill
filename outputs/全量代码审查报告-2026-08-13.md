# PE Reverse Analyzer 全量代码审查报告

- 审查日期：2026-08-13
- 审查范围：Go 控制面、Python 分析引擎与脚本、React/TypeScript 前端、Docker/Compose、CI/CD、依赖与测试体系
- 审查方式：自动化验证 + 关键数据流人工复核
- 结论：当前版本具备可构建的控制台与基础编排骨架，但不满足生产安全上线条件。存在 2 个 P0 组合风险、多个 P1 状态一致性/命令执行/路径隔离问题，以及仍未闭环的多 Agent、PTY 和 ToolCall 执行语义。

## 1. 执行摘要

最高风险来自两条能力在实际生产配置中的组合：

1. `analyst` 角色可调用通用终端接口，控制面通过 `cmd /c` 或 `bash -lc` 执行用户提交的任意命令。
2. 阿里云生产 Compose 将 `/var/run/docker.sock` 挂载给同一个 Web 控制面，并将进程加入 Docker socket 对应组。

这意味着一旦 analyst 凭据被滥用，攻击面不再局限于单个实验工作区，而可能扩展到 Docker daemon 和宿主机。`read_only`、`cap_drop`、`no-new-privileges` 无法抵消 Docker socket 本身提供的控制能力。

在继续扩展 PentAGI 式前端和编排功能前，应先完成终端隔离、Docker worker 拆分、服务端 RBAC/HTTP 方法约束、路径真实解析、worker CAS/lease 和遗留 `shell=True` 修复。

## 3. 详细发现

### RA-001：控制面任意 shell 命令执行（P0）

**位置**

- `cmd/reverse-analyzer-server/main.go:688`
- `cmd/reverse-analyzer-server/main.go:1275`
- `cmd/reverse-analyzer-server/main.go:1283`
- `cmd/reverse-analyzer-server/auth.go:219`
- `cmd/reverse-analyzer-server/auth.go:276`

**证据与数据流**

`POST /api/experiments/{id}/terminal` 的 `command` 字段未经命令白名单或参数化解析，直接进入：

```go
exec.CommandContext(ctx, "cmd", "/c", session.Command)
exec.CommandContext(ctx, "bash", "-lc", session.Command)
```

非 GET、非 providers、非显式 execute 后缀的接口默认映射为 `analysis.plan`；`analyst` 拥有该权限。因此该能力不是仅管理员可用。

**影响**

- 读取控制面容器内可访问的配置、工作区和运行时信息。
- 修改工作区、生成持久化内容或消耗主机资源。
- 与 Docker socket 组合后扩大为容器和宿主机控制风险。

**修复建议**

1. 立即在生产关闭通用 `/terminal`。
2. 将终端能力迁移到独立、短生命周期、无 Docker socket、无 secrets、只挂载单实验目录的 worker。
3. 服务端只允许结构化命令模板和参数数组，不接受 shell 字符串。
4. 为终端引入独立权限 `terminal.execute`，默认仅 admin 或专门运行角色拥有。
5. 增加 CPU、内存、进程数、时间、输出和磁盘配额。

### RA-002：Web 控制面暴露 Docker socket（P0）

**位置**

- `deploy/compose.aliyun.yml:28`
- `deploy/compose.aliyun.yml:49`
- `deploy/compose.aliyun.yml:61`

**证据**

```yaml
group_add:
  - "${DOCKER_GID:?set DOCKER_GID}"
REVERSE_ANALYZER_SANDBOX_RUNTIME: docker
volumes:
  - /var/run/docker.sock:/var/run/docker.sock
```

**影响**

Docker daemon API 通常等价于宿主机高权限控制。Web 控制面同时处理用户请求、Provider 配置和实验数据，不应直接拥有该能力。

**修复建议**

- 从 Web 服务移除 Docker socket 和 `DOCKER_GID`。
- 使用独立 worker/runner 服务承接 sandbox 创建，采用最小 RPC 接口和任务签名。
- worker 只允许固定镜像、固定挂载根目录、只读根文件系统和严格资源限制。
- 对实际 `compose.aliyun.yml` 建立 CI 安全断言，而不是只检查另一份 Compose。

### RA-003：CMake 阶段执行不可信工程逻辑（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go:1407`
- `cmd/reverse-analyzer-server/main.go:1408`

**说明**

`cmake -S <project> -B <buildDir>` 会执行 `CMakeLists.txt` 中的 `execute_process()`、自定义命令和配置期逻辑。当前命令在控制面环境直接运行，日志中标记 `isolated: true` 不等于实际隔离。

**修复建议**

所有源码配置、构建和测试都必须在独立 sandbox worker 中执行；控制面只提交任务并收集受限产物。

### RA-004：源码路径符号链接逃逸（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go:1471`
- `cmd/reverse-analyzer-server/main.go:1492`
- `cmd/reverse-analyzer-server/main.go:1520`

**说明**

`safeProjectFile()` 仅通过 `Abs + Rel` 做词法边界检查，没有对项目根、现有父目录和最终目标执行 `EvalSymlinks`。如果工程内存在指向工程外的目录符号链接，写入、复制、移动和删除可能落到工程外。

**修复建议**

- 对根目录和目标已存在父目录执行真实路径解析。
- 拒绝路径链上的任何 symlink/reparse point，或在解析后验证真实路径仍位于真实根目录内。
- 使用 `Lstat` 而非仅 `Stat`。
- 新增 Linux symlink 和 Windows junction/reparse point 回归测试。

### RA-005：HTTP 方法和 RBAC 组合越权（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go:688`
- `cmd/reverse-analyzer-server/main.go:700`
- `cmd/reverse-analyzer-server/auth.go:261`

**说明**

`terminal` 和 `tool-calls` 路由在分派层没有强制 mutation 方法。权限函数先将所有 GET/HEAD 映射为 `workspace.read`，因此 viewer 对精心构造的 GET mutation 请求可能通过鉴权。`terminalSessions()` 对所有非 GET 方法都进入创建逻辑，也未明确只接受 POST。

**修复建议**

- 路由层和 handler 层双重强制方法。
- RBAC 按命名路由/动作映射，不以 GET/HEAD 作为通用只读推断。
- 对所有 mutation 加 CSRF/Origin 策略（如使用 Cookie）和审计事件。

### RA-006：ToolCall retry/cancel 没有真实执行语义（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go` 的 `toolCallAction`
- `frontend/src/App.tsx:2318`

**说明**

重试只是把原 ToolCall 状态改为 `queued`，没有创建新 attempt、入队、绑定 executor 或执行；取消也没有中断运行中的 context/process。前端却显示“工具调用已重新排队”，形成错误成功反馈。

**修复建议**

- 以不可变 attempt 模型记录重试：`original_call_id`、`attempt`、`queued_at`、`worker_id`。
- executor 持有每个 ToolCall 的 cancel context。
- 状态转换必须由队列和 worker 驱动，前端操作后重新拉取编排快照。

### RA-007：worker 终态覆盖与保存失败被忽略（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go:1977`
- `cmd/reverse-analyzer-server/main.go:1990`
- `cmd/reverse-analyzer-server/main.go:2175`

**说明**

worker 收尾重新加载实验并直接写入 `failed/completed/partial`，没有检查记录是否已被取消或版本是否变化。多个 `_ = s.saveExperiment(...)` 忽略持久化错误，随后仍可能发布完成事件，造成 API、事件流和数据库状态不一致。

**修复建议**

- 增加 `version` 和 compare-and-swap 更新。
- 取消终态不可被普通 worker 收尾覆盖。
- 只有持久化成功后才能发布终态事件。
- 为事件和状态写入使用事务/outbox。

### RA-008：多副本缺少 lease 和单写者约束（P1）

**说明**

当前任务恢复和 worker 执行没有 `worker_id`、lease、heartbeat 或 fencing token。多副本启动时可能重复恢复、误标记或同时推进同一任务。文件后端也存在整条 JSON 覆盖导致 history/artifacts/orchestration 丢失的可能。

**修复建议**

- PostgreSQL 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 或显式 lease 表。
- 引入 heartbeat、lease expiry、fencing token 和幂等 attempt。
- 文件后端仅用于单进程开发模式，生产强制 PostgreSQL。

### RA-009：Python `shell=True` 命令注入（P1）

**位置**

- `scripts/common.py:273`
- `scripts/reconstruct.py:1426`
- `scripts/reconstruct.py:1436`
- `scripts/apk_analyze.py:54`
- `scripts/apk_analyze.py:114`
- `scripts/apk_analyze.py:323`

**说明**

APK 路径和输出路径通过字符串格式化进入 shell，或在 Windows 上以参数列表配合 `shell=True`。恶意文件名中的 shell 元字符可能改变命令语义。

**修复建议**

- 统一使用参数数组和 `shell=False`。
- 使用 `shutil.which()` 检测工具。
- 为外部工具增加超时、输出上限、文件大小和解压预算。

### RA-010：终端资源和生命周期不受控（P1）

**位置**

- `cmd/reverse-analyzer-server/main.go:1303`
- `cmd/reverse-analyzer-server/main.go:1308`
- `cmd/reverse-analyzer-server/main.go:1314`

**说明**

终端输出永久追加到内存，没有总字节/行数上限、TTL 或会话回收。scanner 最大 token 为 1 MiB，超长单行会停止读取，而子进程可能因 stdout 管道阻塞。`cmd.Wait()` 错误被丢弃，取消或失败也无条件标记为 `finished`。

**修复建议**

- 输出使用固定容量 ring buffer + 持久化分块日志。
- 明确 `completed/failed/cancelled/timed_out`。
- 处理 scanner error 和进程 exit code。
- 服务 shutdown 时取消全部会话并等待回收。

### RA-011：Go/Python 状态契约不一致（P2）

**位置**

- `cmd/reverse-analyzer-server/main.go:2173`
- `reverse_analyzer/runtime/experiments.py:22`
- `reverse_analyzer/runtime/experiments.py:240`

Go 会写入 `partial`，Python `_TRANSITIONS` 不包含该值，导致同一实验记录可能无法被 Python CLI 读取或更新。

**修复建议**

使用共享 schema/生成代码统一状态枚举和转换矩阵，并增加跨语言契约测试。

### RA-012：前端状态误报和陈旧状态（P2）

**位置**

- `frontend/src/App.tsx:261`
- `frontend/src/App.tsx:853`
- `frontend/src/App.tsx:876`
- `frontend/src/App.tsx:2318`

**问题**

- ToolCall 操作成功后不刷新编排状态。
- Provider 测试和保存使用的数据路径不一致，未保存 API Key 不一定进入测试请求。
- HTTP 200 即显示“连接成功”，可能掩盖 `dependency-gated`。
- token 失效或切换时，旧 identity/provider 数据可能残留。
- SSE 断开后缺少重连和轮询降级。

**修复建议**

建立统一 API client、标准错误模型、身份切换清理和 mutation 后 revalidation；Provider 测试必须按业务状态而非 HTTP 状态判定。

### RA-013 至 RA-015：供应链与部署基线（P2）

- `requirements.txt`/`pyproject.toml` 使用范围版本，缺少带 hash 的完整 lock。
- Docker 基础镜像、PostgreSQL 镜像和 CI Actions 使用 mutable tag。
- `config/github-tools.lock.json` 含 `releases/latest` 和 `operator-selected`，并非严格 lock。
- `npm audit --omit=dev` 报告 2 high、2 moderate：涉及 Vite/esbuild/nanoid/postcss 依赖链。
- 实际 `deploy/compose.aliyun.yml` 与安全基线 `deploy/compose.production.yml` 不一致，现有测试未覆盖关键漂移。

**修复建议**

锁定依赖、镜像 digest 和 Action SHA；引入 pip-audit、OSV/Trivy、Gitleaks、SBOM、镜像签名和 Compose 安全断言。

## 5. 测试缺口

1. viewer 使用 GET 请求触发 ToolCall mutation。
2. analyst 与 admin 的终端权限边界。
3. 符号链接/junction 父目录逃逸。
4. cancel 与 worker 收尾并发竞争。
5. PostgreSQL 多副本 lease、重复恢复和 fencing。
6. 终态保存失败后的事件一致性。
7. 超长 stdout、无限输出和进程超时。
8. ToolCall 真正重试、取消和 attempt 计数。
9. SSE 断线重连和前端状态 revalidation。
10. Go `partial` 与 Python 存储的跨语言契约。
11. 实际 `compose.aliyun.yml` 的 Docker socket、用户组和 secret 挂载安全断言。
12. APK/IPA 压缩炸弹、条目数、解压总量和外部工具超时。

## 6. 修复顺序

### 第一批：立即阻断生产高风险

1. 禁用生产 `/terminal`。
2. 从 Web 容器移除 Docker socket 和 `DOCKER_GID`。
3. terminal/tool-calls 强制 POST，并引入独立 RBAC 权限。
4. 禁止控制面直接运行 CMake，迁移到独立 worker。

### 第二批：恢复状态与文件边界正确性

1. 修复真实路径校验和 symlink/reparse point 逃逸。
2. 引入 worker lease、version/CAS、取消终态保护。
3. 终态保存成功后再发布事件。
4. ToolCall 使用真实队列、attempt 和 cancel context。

### 第三批：清理遗留执行面和资源风险

1. 移除 Python `shell=True`。
2. 增加归档和外部工具资源预算。
3. 终端日志改为有界存储并实现 shutdown 回收。
4. 统一 Go/Python 状态 schema。

### 第四批：前端与供应链收口

1. 修复 mutation 后刷新、Provider 状态判断和身份清理。
2. 增加 SSE 重连和轮询降级。
3. 锁定依赖、镜像和 Actions。
4. 修复 npm advisory，补充 SBOM、扫描和签名门禁。

## 7. 上线判定

当前判定：**不建议直接生产上线或继续开放 analyst 终端能力**。

达到生产上线最低门槛前，至少必须关闭 RA-001/RA-002，修复 RA-004/RA-005/RA-007/RA-009，并让 Python 回归中的 blocking failure/error 归零。多 Agent、独立 Subtask、真正 PTY 和 ToolCall executor 应在这些基础问题解决后继续实现。
