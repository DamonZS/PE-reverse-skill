### RA-WT-002：Runner 超限 stdout 后可能阻塞在 `cmd.Wait()`（P1）

**Evidence**

- `cmd/reverse-analyzer-runner/main.go:106-125` 建立 stdout pipe、合并 stderr、启动子进程，读取输出后调用 `Wait()`。
- `cmd/reverse-analyzer-runner/main.go:124` 使用 `io.LimitReader(stdout, 64<<20)`。
- `cmd/reverse-analyzer-runner/main.go:125` 在读取结束后才执行 `cmd.Wait()`。

**Finding**

当前实现通过 capped writer 限制响应转发大小，但不以 `LimitReader` 截断 source；`io.Copy` 会继续消费完整 pipe 后再调用 `cmd.Wait()`。已有测试验证超过响应限制时 source 仍被完整读取，因此原先的 pipe 阻塞路径已修复。

**Path**

```text
POST /v1/jobs/run
  -> runJob
  -> worker stdout/stderr pipe
  -> io.LimitReader(64 MiB)
  -> io.Copy returns
  -> cmd.Wait()
  -> child may remain blocked writing pipe
```

**影响**

- 超大输出任务无法稳定结束。
- Go 控制面可能长期占用 job、HTTP 连接和 Runner 资源。
- 任务状态可能停留在 running，造成后续恢复或重试困难。

**修复建议**

1. 继续后台 drain pipe，同时只向响应写入前 64 MiB，并记录截断标记。
2. 将 stdout/stderr 读取、进程等待和响应写入拆成并发协调逻辑，保证 `Wait()` 前 pipe 始终被消费。
3. 增加超大 stdout、stderr、取消和子进程退出的回归测试。

**动态入口误报判断**：不是误报；属于 Go `os/exec` pipe 的确定性生命周期问题。

### RA-WT-003：目录 `callable_name` 可能得到布尔字符串（P1）

**Evidence**

- `frontend/src/api/catalog.ts:10-15` 定义 `callable` 为 boolean、`callable_name` 为 string。
- `frontend/src/api/catalog.ts:57` 正确将 `item.callable` 归一化为 boolean。
- `frontend/src/api/catalog.ts:62` 却直接执行 `callable_name: text(item.callable)`。
- `reverse_analyzer/platform_catalog.py:98-107` 的 builtin tool 记录中，`callable` 实际是函数的 `__qualname__`；但其他目录项和兼容后端响应允许 `callable` 是 boolean，因此前端必须按字段优先级处理。

**Finding**

当后端返回 `{ "callable": true }` 或 `{ "callable": false }` 时，前端详情数据会产生 `callable_name: "true"` 或 `"false"`。这会把能力状态误当成调用入口名称，影响平台目录详情和诊断信息。

**Path**

```text
/api/platform/catalog JSON
  -> fetchCatalog
  -> normalizeItem
  -> callable_name = text(item.callable)
  -> UI displays boolean as callable entry name
```

**修复建议**

使用 `item.callable_name`、`item.entrypoint` 或 `item.module` 的明确字段；只有在字段确实为字符串时才回退到 `item.callable`。同时增加真实 JSON fixture 测试，覆盖 boolean、function-name 和缺失字段三种形状。

**动态入口误报判断**：不是误报；静态类型声明与赋值逻辑直接矛盾。

包环境中某个 Provider 的依赖缺失时，CLI 会进入直接脚本执行 fallback，随后可能报出 `cannot import name 'AnalyzerConfig' from 'config'`，而不是报告真正缺失的 `pefile` 或其他模块。该行为降低诊断准确性，也可能让部分 CLI 子命令整体不可用。

**修复建议**

只在确认是相对导入失败且当前确实为脚本执行时才使用 fallback；对可选 Provider 使用延迟导入或显式 dependency-gated 状态；保留原始异常链并输出依赖名称。

**动态入口误报判断**：不是误报；此前已在缺少 `pefile` 的环境中复现错误被二次掩盖。

### RA-WT-008：Capability Registry 不会自动 fallback 到后续 Provider（P2）

**Evidence**

- `reverse_analyzer/core/capabilities/registry.py:13-15` 按 priority 排序 Provider。
- `reverse_analyzer/core/capabilities/registry.py:23-34` `resolve()` 默认返回第一个 Provider，preferred 只按名称查找。
- 未发现 `resolve()` 在 `supports()` 为 false 时继续遍历后续 Provider 的逻辑。

**Finding**

同一 Capability 注册多个 Provider 时，priority 只决定首选项；如果调用方没有自行实现 fallback，首选 Provider 不支持目标不会自动转到备用 Provider。该设计可能是有意的显式选择，但不能被误解为自动容灾或能力协商。

**修复建议**

明确 API 语义：要么将 `resolve()` 命名为 `resolve_preferred()` 并由调用方显式筛选，要么增加 `resolve_supported(context)`，按 `supports()` 逐个尝试并记录拒绝原因。为 mock/备用 Provider 增加测试。

**动态入口误报判断**：不是死代码；这是已接线实现的能力限制，不应直接删除或改成隐式行为。

### RA-WT-009：SkillCatalog 初始化吞掉路由校验异常（P2）

**Evidence**

- `reverse_analyzer/skills/catalog.py:58-63` 构建 `SkillRouter` 失败时捕获 `SkillRoutingError` 并 `pass`。
- `reverse_analyzer/skills/catalog.py:117-120` 后续 audit 才将错误包装为 `skill_runtime.status=unavailable`。

**Finding**

目录发现和路由校验被分离后，调用方可能只使用 `discover()` 的结果而忽略 audit 状态，从而看到“技能存在”却不知道 route 已损坏。配置错误被降级处理，容易产生半可用目录。

**修复建议**

在返回目录元数据中始终暴露 routing status 和错误；对需要路由的生产入口在状态为 unavailable 时显式失败；不要让异常吞掉后继续形成看似完整的 catalog。

**动态入口误报判断**：不是误报；代码明确吞掉异常。但是否要保留宽容模式需结合 CLI 兼容目标决定。

### RA-WT-010：`catalog_coverage_percent=100` 容易被误解为接入率（P2）

**Evidence**

- `reverse_analyzer/platform_catalog.py:47-52` 将 `cataloged_total` 设置为 `discovered_total`，并返回 `catalog_coverage_percent: 100.0`。
- 同一位置的 `meaning` 已说明该指标与 dependency readiness、live acceptance 分离。

**Finding**

实现语义本身是自洽的，但字段名“coverage”容易在前端或运营层被理解为“可调用覆盖率”。目录记录中的 `callable`、`dependency_ready`、`accepted` 是不同维度，单一 100% 指标不能证明真实执行链路可用。

**修复建议**

把字段改为 `discovery_catalog_coverage_percent`，并同时展示 `callable_count`、`dependency_ready_count`、`accepted_count`、`live_ready_count`。前端文案应避免将 catalog 覆盖率显示为平台接入率。

**动态入口误报判断**：不是 bug 级误报；这是接口命名和消费风险，已有注释减轻但没有完全消除风险。

### RA-WT-011：Skill/Tool 注册边界存在未闭环资产（P2）

**Evidence**

- `routing.json` 的 route/subskill 集合包含 `dotnet-reverse`，例如 `routing.json:378`。
- `tool-manifest.json:182-185` 声明 `refresh-skill-index`，但未发现 route 的 `tools` 数组使用该工具。
- `reverse-skills/skills/pentest-tools/src-hunter/SKILL.md` 在工作树存在，但未发现其作为 route 或 manifest skill ID 注册。
- 当前严格索引验证通过，说明主 route/index 集合内部一致，但不等于所有仓库 Skill 都进入主路由。

**Finding**

存在三类资产状态：主 route、subskill、仓库孤立 Skill/manifest tool。状态没有在目录中统一表达，维护者容易误以为“文件存在”即“可被主路由调用”。

**修复建议**

定义并验证 `route`、`subskill`、`inventory-only` 三种明确状态；对 `src-hunter` 选择补 route/manifest 或明确 inventory-only；对 `refresh-skill-index` 标记为治理工具并从普通运行时目录分离，避免误当业务工具。

**动态入口误报判断**：不是无效文件结论；这些资产可能是有意的治理或子技能，但当前注册语义需要显式化。

### RA-WT-012：ToolCall retry/cancel 的执行语义必须与 UI 状态一致（P2）

**Evidence**

- `cmd/reverse-analyzer-server/main.go:1583-1585` 的 `defaultToolCallExecutors()` 返回空 map。
- `frontend/src/App.tsx:2335-2338` 已针对 `dependency-gated` 显示“已创建 successor attempt，但该调用缺少安全重放执行器”，其他状态则显示“已创建并启动 successor attempt”。
- `frontend/src/App.tsx:2428-2429` 暴露 retry/cancel 操作。

**Finding**

当前 UI 已部分修正了 dependency-gated 情况，但默认 executor 为空意味着 retry 的成功含义是“创建后继 attempt”，不是“已经执行”。cancel 是否能中断真实进程也取决于是否存在运行 executor。若其他后端状态仍返回 queued/running，用户可能将记录状态理解为实际执行状态。

**修复建议**

将 attempt 创建、队列入队、executor 执行和取消分别建模；API 返回 `accepted`、`queued`、`started`、`dependency_gated` 等明确状态；前端只根据服务端状态刷新，不用操作 HTTP 200 推断已执行。

**动态入口误报判断**：不是死代码；后端是预留扩展点，问题在当前能力边界和 UI 语义必须保持一致。

### RA-WT-013：部署测试没有验证完整 YAML/entrypoint/Runner 语义（P2）

**动态入口误报判断**：不是误报；测试能力边界是确定事实，不表示当前 Compose 必然错误。
