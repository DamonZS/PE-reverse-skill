# Skill Parity Matrix

Status is based on executable production paths in this checkout.

## Status Semantics

- `done`: the named scope has an executable production path and non-mock tests for its core behavior.
- `dependency-gated`: a production path exists, but parity acceptance still requires an external runtime, toolchain, platform, or live target that has no checked-in real end-to-end fixture. This is not `done`.
- `partial`: production code implements only a strict subset of the named scope.
- `missing`: no production implementation exists for the named scope.
- A schema, registry entry, mock/fake backend, injected fake runner, or graceful `unavailable` result documents a boundary only; it never upgrades status.
- `live-verified` is a separate fixture acceptance state, not a substitute for the capability statuses above. It requires a retained hash-backed acceptance record whose fixture contract, target identity, structured execution proof, artifact hashes, provenance, rollback, and cleanup all verify.
- At this checkpoint, six bounded P1 fixtures have that formal state: `p1-memory-runtime-live`, `p1-loadlibrary-injector`, `p1-manual-map-live`, `p1-native-hook-live`, `p1-hook-target-resolution`, and `p1-native-debugger-child`. A successful smoke without such a record remains `repository-ready`, `ready-to-run`, or `dependency-gated` as reported by its fixture contract.

## Runtime and Dependency Limits

- `memory_raw_runtime` has a real Win32 backend and a formally `live-verified` registered acceptance fixture for its bounded controlled-child scope. The record binds the immutable fixture contract and target identity, requires two executed and zero skipped tests with positive live-operation count, hashes all retained artifacts, and verifies rollback and cleanup. Arbitrary targets and environments outside that named scope are not implied.
- `structured_memory_layout_engine` is complete for its bounded offline schema scope. `structured_memory_live_runtime` remains dependency-gated outside the accepted child-process schema read/write subset because live pointer-chain and module+RVA evidence is not part of the retained Memory Runtime record.
- `injector` executes real Win32 `LoadLibraryW` injection and a bounded x64 manual-map path with rollback. Both bounded paths now have retained target-bound live records. The capability remains dependency-gated only for claims beyond those fixtures, including broader architecture, loader, privilege, and target coverage.
- `frida_local_dynamic_trace` has a real local attach/spawn path, but Frida and a live local target are external dependencies and checked-in execution tests use `FakeHookRuntimeBackend`.
- `native_trampoline_vtable_hooking` and `debugger_hardware_breakpoint` now have distinct native Win32 implementations, not Frida labels. They remain dependency-gated because ordinary tests use `FakeWin32Backend`; the checked-in VTable/trampoline and hardware-debugger smoke tests are opt-in, and inline relocation also depends on Capstone.
- `patch_planner` implements offset/RVA/AOB, code-cave, section-extension, resource, IAT-thunk, entrypoint, and overlay-preserving strategies. Executable-section instruction-boundary validation requires Capstone and fails closed when Capstone is absent.
- `engine_static_analysis` is separated from `engine_native_mapping_runtime_extraction`: static IL2CPP metadata-to-PE mapping, a bounded read-only Win32 runtime provider, and strict ingestion of collector-provided Mono/IL2CPP/Unreal runtime dumps now exist. Runtime extraction remains `partial` because the dump parser is not a production live collector, complete Unreal object/class/function/UMG traversal and proven `GWorld` layouts are absent, and controlled dumps/synthetic memory do not prove a live Unity/Unreal E2E.
- `android_package_analysis` is a real bounded static parser. `android_rebuild_orchestration` and `android_java_decompilation` remain dependency-gated because fake command runners and graceful missing-tool reports do not prove real `apktool`/`apksigner`/Jadx execution.
- `android_native_patch_pipeline` has real ELF-aware planning, APK ZIP-copy patching, verification, rollback proof, and optional `apksigner` execution. It remains dependency-gated because checked-in success coverage uses synthetic ELF/APK fixtures and no real application/signing-credential E2E exists; an unsigned output is not evidence of completed signing.
- `ios_static_analysis` is complete only for bounded offline IPA/plist/resource/framework/Mach-O-header/semantic-IR inspection. Encrypted-code decompilation, rebuild/re-signing, and dynamic iOS analysis are outside that `done` scope.
- `android_dynamic_instrumentation` has a production Android Frida adapter, but fake device sessions and graceful missing-Frida results do not prove execution on a real Android package; it remains dependency-gated with no checked-in real-device E2E.
- `protocol_offline_analysis` uses a built-in PCAP/PCAPNG parser. Without `msgpack`, affected MessagePack decoding is explicitly partial. `network_udp_loopback_runtime` and the TCP loopback path use real IPv4 loopback sockets, while the broader `network_capture_mutation_replay` capability remains `partial` because IPv6, arbitrary-interface, remote, TLS/HTTP, and general replay paths are absent.
- `graphics_present_runtime` has a production passive PresentMon parser/orchestrator and D3D11/D3D12/OpenGL/Vulkan native-bridge protocol, but generated captures do not prove a real bridge or live graphics target. `gdi_overlay_runtime` provides an external layered window and its gated smoke passed on this host, without retained acceptance artifacts. `imgui_in_process_rendering` now has a D3D11 project/build provider and a strict host lifecycle orchestrator, but checked-in host success uses a synthetic bridge. The broader `render_overlay_runtime` remains `partial` because these pieces do not yet form one live graphics-hook, matrix-acquisition, projection, and diagnostic-overlay loop.
- `world_projection_and_diagnostic_overlay` contains a complete bounded offline projection engine for caller-supplied matrices, but remains `partial` as a combined capability: it does not acquire live matrices or feed projected entities into a live overlay frame loop. `automated_target_control` likewise remains `partial`; its deterministic scoring, smoothing, recoil, and trigger logic is explicitly offline simulation and never emits input.
- `kernel_driver_memory_runtime` contains a production versioned client and native lab-driver source, but ordinary tests do not load the driver. `hardware_identity_virtualization` contains real snapshot collection and a production external-helper transport, but no virtualization helper is checked in. `dma_memory_runtime` contains read-only translation/read/snapshot logic plus MemProcFS/LeechCore adapter boundaries, but no real DMA-device acquisition fixture exists. All three remain dependency-gated.
- `windows_uia_runtime` uses a production `comtypes` UIAutomationClient adapter, but fake COM tests and `unavailable` dependency reports do not close its live desktop gate. `vlm_visual_provider` has production plugin loading/validation, but mock plugins do not prove a real model. `gui_analysis` therefore remains `partial` for broad runtime and visual parity.
- `llm_jailbreak_campaign_engine` is the Active Model Jailbreak Tool. Its standalone CLI, five campaign modes (`builtin`, PAIR, TAP, Crescendo, Evolution), heuristic/model semantic judges, repository-backed instruction profiles, OpenAI-compatible HTTP transport, Registry provider, artifacts, and platform integrations are production paths. `reverse-skills/`, `scripts/codex-instruct-examples/`, and `scripts/codex-instruct.py` are first-party assets using the shared instruction-bundle registry; the script deploys bundles to Codex installations and is not a per-round campaign runtime. Provider planning seals a complete digest-verified instruction-bundle snapshot and execution consumes that snapshot without rereading source files. Repository-external Markdown uses content-addressed public provenance, while host absolute paths remain isolated from campaign artifacts, reports, manifests, and Dashboard data. Check-level `discovered` means a dependency was found without a successful executed probe; `verified` means only that the bounded import/version/capability probe succeeded. Workflow `dependency_gated` is rendered as `dependency-gated` and means the production path is still gated by probe, external runtime/toolchain, or live-target E2E evidence. The Dashboard selects the newest valid workspace-confined report, but none of these report states upgrades capability parity by itself.
- `capability_outcome_kb` atomically records bounded outcome history and recommendations. Mocked or unavailable executions are stored as non-success evidence; the knowledge base never turns those records into proof that a capability is implemented.

## External Environment Acceptance Boundary

Dependency discovery, protocol validation, synthetic fixtures, and a real target E2E are separate evidence levels. `environment validate --execute-probes` can establish that a dependency or bridge responds to its bounded capability probe; it cannot prove that the dependency operated correctly against the analyzed target. A `dependency-gated` row becomes `done` only when the named scope has a repeatable, checked-in acceptance fixture using the production provider and the required external environment.
