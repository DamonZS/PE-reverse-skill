# P0-P4 Acceptance Contract

This document defines how P0-P4 implementation readiness is interpreted. The
machine-readable source is the latest workspace-confined
`environment-validation.json` generated by:

```powershell
python -m reverse_analyzer environment validate --execute-probes --json --out <directory>
```

The report's `acceptance_fixtures` array is the canonical fixture inventory.
Do not maintain a second hand-written JSON copy of that inventory.

## Evidence states

| State | Meaning |
|---|---|
| `repository-ready` | Code, contract, deterministic fixtures, and an acceptance command exist in the repository. |
| `ready-to-run` | The required host and declared environment gates are present, so the acceptance command can run. |
| `dependency-gated` | A required executable, module, toolchain, bridge, fixture, device, or environment gate is absent or unverified. |
| `unsupported-host` | The current host cannot execute that fixture. |
| `live-verified` | The named production fixture was actually executed and its target-bound artifacts were retained and reviewed. |

`repository-ready` does not mean a live target was exercised.
`ready-to-run` does not mean the command was run. A discovered dependency or a
successful bounded probe does not establish target-level correctness.

The base environment validator deliberately emits `live_verified: false`.
Only a separate target-specific acceptance run may promote a fixture to
`live-verified`. Passing `--acceptance-workspace` to `environment validate`
includes retained record history, but promotes a fixture only when the selected
record's integrity verification still succeeds. That record must preserve:

- fixture id and acceptance command
- the registered fixture contract SHA-256 and immutable structured argv
- session id and target identity
- provider and external-tool versions
- command inputs and configured gates
- expected and observed artifacts
- SHA-256 and size for every retained observed artifact
- structured execution proof for live fixtures
- cleanup or rollback result
- final pass/fail outcome

## Acceptance record infrastructure

The executable record workflow is:

```powershell
python -m reverse_analyzer environment accept list --workspace <workspace>
python -m reverse_analyzer environment accept run --fixture <fixture-id> --workspace <workspace> --execute --timeout 300
python -m reverse_analyzer environment accept verify --record <record.json>
python -m reverse_analyzer environment validate --json --acceptance-workspace <workspace>
```

`environment accept run` accepts only a registered fixture id. It resolves an
immutable argv contract, replaces only the registered Python placeholder, runs
with `shell=False`, applies the fixture timeout, and writes isolated outputs to
`acceptance/runs/<fixture-id>/<session-id>/`. The corresponding record is
stored under `acceptance/records/` and binds the fixture contract hash,
readiness result, target identity, output hashes, provenance, rollback,
cleanup, and outcome.

For a live evidence level, exit code zero is necessary but insufficient. The
registered `execution_proof_artifact` must be a unique structured JSON object
with a successful status, `executed_tests` at or above the fixture minimum,
`skipped_tests: 0`, and `live_operations > 0`. Missing, malformed, synthetic,
all-skipped, or below-minimum proof keeps `live_verified: false`, even when the
test process exits successfully. Verification later recomputes every retained
artifact hash, checks the current registered fixture contract hash, and
revalidates the execution proof. Tampering therefore removes the live claim
when records are merged into an environment report.

Six P1 fixtures are formally live-verified at this checkpoint:

- `p1-memory-runtime-live`
- `p1-loadlibrary-injector`
- `p1-manual-map-live`
- `p1-native-hook-live`
- `p1-hook-target-resolution`
- `p1-native-debugger-child`

Each selected record has a current fixture-contract hash, target identity,
non-skipped structured execution proof, positive live-operation count,
artifact hashes, provenance, and the rollback or cleanup proof required by its
contract. These promotions are limited to the bounded controlled-target scopes
named by those fixtures; they do not establish arbitrary-process,
cross-architecture, cross-version, or Frida parity.

## Phase boundaries

### P0

P0 is repository-ready when environment schema v2 is generated, P0-P4 fixtures
are validated, and the Dashboard renders readiness separately from live proof.

### P1

Provider contracts and deterministic tests establish repository readiness for
injection, hook runtime, hook-target resolution, and native debugging. The six
registered fixtures listed above are `live-verified` for their bounded Windows
controlled-target scopes. Frida attach/spawn and any broader target,
architecture, privilege, or OS matrix still require separate registered
fixtures and retained evidence.

### P2

All seven PE patch strategies now have a formal repository-production record
covering plan, verify, apply, risk, rollback metadata, source immutability, and
the real patch provider lifecycle. DLL proxy generation has a formal toolchain
record covering CMake/Ninja/MinGW compilation and export-surface validation.
A named host load/unload fixture is still required for a live host claim.

### P3

Synthetic process-memory backends and generic child-process reads validate
parsers and safety boundaries, not Unity or Unreal target parity. Live Mono,
IL2CPP, and Unreal fixtures are required for engine-version-specific claims.

### P4

Generated captures, bridge protocol tests, project generation, and fake render
backends validate contracts only. Live Present observation, a host-owned ImGui
load/hook lifecycle, device-loss recovery, and interactive overlay teardown
must be demonstrated against named graphics fixtures before P4 is live-verified.

## Review rule

Capability status in `docs/skill_parity_matrix.md` must never be upgraded from
`partial` or `dependency-gated` solely because an optional dependency was found,
a mock/synthetic fixture passed, or a provider returned a valid schema.

## Artifact retention policy

Acceptance workspaces are generated evidence, not source files. Local runs may
use `.codex-tmp-*` directories, but those directories must remain ignored and
must not be committed. Keep the executable fixture contracts and this curated
checkpoint in the repository. When a release requires retained evidence,
publish only the reviewed summary or manifest under `docs/acceptance/`, and
store the full raw workspace in the designated external evidence archive.

Python packages used to execute acceptance tests belong in an ignored virtual
environment such as `.venv/`; dependency trees must not be vendored through a
temporary acceptance directory.
